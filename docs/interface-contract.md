# Контракт интерфейса: создание заявки

Версия: **1.0**. Дата: **17.11.2026**. Состояние: **описан реализованный прототип; ожидает ревью**.

## 1. Выбор операции

**Операция:** HTTP-запрос `POST /tickets`.

**Назначение:** создать заявку технической поддержки по заголовку и получить её идентификатор и начальный статус.

**Связь с ЛР2:** [FR-2 и US-2 — создание заявки](01-requirements.md). Операция реализует только фрагмент сценария: ввод заголовка, создание и выдачу результата. Авторизация, описание, категория и автор заявки из целевой спецификации пока не реализованы. Контракт ниже описывает фактический работающий интерфейс, а не будущую версию API.

**Реализация:**

- [router.go](../src/internal/api/http/router.go) — регистрация `POST /tickets`.
- [tickets.go](../src/internal/api/http/tickets.go) — обработчик `ticketsHandler.create`.
- [dto/ticket.go](../src/internal/api/http/dto/ticket.go) — `CreateTicketRequest`, `TicketResponse`.
- [service/tickets.go](../src/internal/service/tickets.go) — `Create`, обрезка пробелов и проверка заголовка.
- [store/memory.go](../src/internal/store/memory.go) — сохранение и назначение ID.

## 2. Вызывающая сторона и условия

Вызывающая сторона — HTTP-клиент, например curl или другой компонент. Пользовательская роль в целевой системе — заявитель; в текущем прототипе вход не требуется и проверка роли отсутствует. Интерфейс предназначен для локальной демонстрации.

Сервер должен быть запущен по инструкции [README](../README.md#запуск). Базовый адрес по умолчанию `http://127.0.0.1:8080`; при другом порте заменить адрес в примерах. Для работы операции не нужны БД, Kafka, ключи или внешние API. Данные хранятся в памяти одного процесса и исчезают после его перезапуска.

| Параметр вызова | Значение |
| --- | --- |
| Метод | POST |
| Путь | /tickets |
| Заголовок запроса | Content-Type: application/json |
| Авторизация | Не требуется в текущем прототипе |
| Параметры пути и query | Не требуются |
| Тело | Один JSON-объект с полем title |

Заголовок Content-Type следует передавать как указано, хотя текущий обработчик его значение не проверяет. Повторный успешный вызов создаёт новую заявку: идемпотентность не предусмотрена.

## 3. Входные данные

| Поле | Тип | Обязательность | Допустимые значения |
| --- | --- | --- | --- |
| title | string | Обязательно | Строка, непустая после удаления начальных и конечных Unicode-пробелов через strings.TrimSpace; внутренние пробелы сохраняются |

Для корректного вызова тело должно содержать только этот объект без дополнительных полей и последующего содержимого. Поддерживаемый размер тела — до 4096 байт в UTF-8 включительно; отдельного ограничения числа символов нет. Значения description, category_id и другие поля не поддерживаются и отклоняются как неизвестные. Пропущенное title, null вместо title, пустая строка и строка из пробелов приводят к выбранной ошибке 400. Число или объект вместо строки также дают 400.

Особенности текущего обработчика: он декодирует только первый JSON-объект и не проверяет конец потока. Поэтому не гарантируется отклонение данных после первого объекта и oversized-запроса, если лишние байты остались непрочитанными. Это ограничение реализации, а не разрешённый способ вызова; строгая проверка и отдельный 413 предусмотрены целевой NFR-5, но сейчас не реализованы полностью.

## 4. Результат успешного вызова

HTTP-статус: **201 Created**. Content-Type: **application/json**. Тело — JSON-объект; после него сериализатор добавляет перевод строки.

| Поле ответа | Тип | Значение |
| --- | --- | --- |
| id | integer | Положительный ID новой заявки, начинается с 1 и увеличивается для каждого успешного создания в текущем процессе |
| title | string | Заголовок после удаления пробелов по краям |
| status | string | Всегда open при создании |

Побочный эффект: в хранилище появляется ровно одна новая заявка. Её можно увидеть через `GET /tickets`. При параллельных вызовах ID назначаются в порядке захвата блокировки, а не гарантированно в порядке начала запросов. ID не глобальный и не сохраняется после перезапуска.

## 5. Характерная ошибка

**Случай:** title пустой после TrimSpace.

- HTTP-статус: **400 Bad Request**.
- Content-Type: **text/plain; charset=utf-8**.
- Точное тело с завершающим переводом строки:

```text
expected JSON with non-empty title (max 4096 bytes)
```

Новая заявка не создаётся, ID не расходуется, существующие заявки не меняются. Такая же ошибка используется при ошибке декодирования JSON, неверном типе title и неизвестных полях; отдельного машинного кода причины сейчас нет. Это отличается от планируемых JSON-ошибок спецификации ЛР2. Вызывающая сторона распознаёт ошибку по статусу 400 и указанному тексту; формат ответа нельзя безусловно считать JSON.

## 6. Два примера

### 6.1. Успешное создание: FR-2 / US-2

Условие для точного ID: только что запущен новый экземпляр приложения, заявок нет, других клиентов нет. Если smoke-сценарий уже выполнялся, перезапустить приложение либо ожидать следующий ID, а не обязательно 1.

Вызов:

```sh
curl -i -sS -X POST http://127.0.0.1:8080/tickets \
  -H 'Content-Type: application/json' \
  --data '{"title":"  Не работает VPN  "}'
```

Ожидаемые существенные части ответа (служебные Date и Content-Length могут отличаться):

```http
HTTP/1.1 201 Created
Content-Type: application/json

{"id":1,"title":"Не работает VPN","status":"open"}
```

Состояние после вызова: одна заявка с ID 1, обрезанным заголовком и статусом open.

### 6.2. Ошибка пустого заголовка: FR-2 / US-2

Выполнить после первого примера:

```sh
curl -i -sS -X POST http://127.0.0.1:8080/tickets \
  -H 'Content-Type: application/json' \
  --data '{"title":"   "}'
```

Ожидаемые существенные части ответа:

```http
HTTP/1.1 400 Bad Request
Content-Type: text/plain; charset=utf-8

expected JSON with non-empty title (max 4096 bytes)
```

Состояние после ошибки: всё ещё одна заявка с ID 1. Проверка:

```sh
curl -sS http://127.0.0.1:8080/tickets
```

Ожидаемое тело:

```json
[{"id":1,"title":"Не работает VPN","status":"open"}]
```

curl без --fail возвращает код завершения 0 и для HTTP 400; в этой проверке нужно смотреть именно HTTP-статус и тело.

Проверка обоих примеров выполнена 17.11.2026 в новом контейнере: статусы, типы содержимого, тела ответов и отсутствие записи при ошибке совпали с контрактом. [Протокол](../evidence/interface-contract.txt).

## 7. Ревью и завершение ЛР3

1. Создать PR lab-3 → main со ссылкой на этот файл.
2. Другой студент составляет вызов по контракту и оставляет в PR данные запроса и ожидаемый ответ либо конкретное уточнение. Автор сам себе ревью не засчитывает.
3. Автор отвечает, при необходимости исправляет контракт отдельным коммитом в lab-3 и закрывает обсуждение после решения замечания.
4. После одобрения и успешных проверок слить PR, поставить тег lab-3 на итоговый коммит main.

Подготовка документа не подтверждает ревью, approve, слияние или публикацию тега. Заголовок PR: `document POST /tickets contract for FR-2 and US-2`. В описании указать реализованный фрагмент, ссылку на контракт и результат проверки двух примеров.
