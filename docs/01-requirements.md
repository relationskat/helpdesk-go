# Описание проекта и требования

Версия документа: **1.0**. Дата: **13.11.2026**. Статус: **подготовлен к ревью, одобрение не получено**.

## 1. О приложении

HelpDesk Go учитывает обращения пользователей небольшой организации в техническую поддержку: вместо разрозненной переписки сохраняет заявку, ответственного, состояние и обсуждение. Проект новый, индивидуальный; автор — relationskat.

**Роли:** заявитель создаёт и отслеживает только свои обращения; специалист видит общую очередь, принимает заявку и обрабатывает её. Одна учётная запись имеет одну роль. Специалист может читать все заявки и комментировать незакрытые; менять статус может только назначенный исполнитель. Учётные записи и категории предварительно создаются администратором через начальное наполнение данных; отдельная роль администратора и интерфейс управления справочниками в объём не входят.

**Уже есть на старте ЛР2:** GET /healthz, POST /tickets с одним полем title, GET /tickets с общим списком. Заголовок обрезается по краям и проверяется на непустоту; выдаются числовой ID и статус open. Хранение в памяти, роли, описание, категории и авторизация отсутствуют. Маршруты — src/internal/api/http/router.go; DTO — src/internal/api/http/dto/ticket.go; логика — src/internal/service/tickets.go. Существующий API — прототип, не подтверждение выполнения будущих правил доступа.

**Термины:**

| Термин | Значение |
| --- | --- |
| Пользователь | Учётная запись с ролью заявителя или специалиста |
| Заявка | Обращение с автором, заголовком, описанием, категорией, исполнителем и статусом |
| Комментарий | Сообщение пользователя в обсуждении заявки с датой и временем |
| Категория | Элемент справочника направлений поддержки |
| Исполнитель | Назначенный на заявку специалист |
| open | Заявка создана; может ожидать назначения либо уже иметь исполнителя |
| in_progress | Назначенный специалист начал обработку |
| closed | Обработка завершена; данные и обсуждение доступны для чтения |

Ниже описывается целевая система семестра. Полные пользовательские сценарии пока планируются; их существующие фрагменты отмечены отдельно. Вне объёма: полноценный UI, регистрация и восстановление пароля, вложения, email, SSO, SLA, повторное открытие и переназначение заявок. Клиент — HTTP/JSON, для демонстрации используется curl.

## 2. Требования к функционалу

### 2.1. Функциональные требования

Приоритет «обязательно» означает обязательную реализацию в этом семестре. Все восемь функций составляют минимальный согласуемый объём; дополнительных пожеланий в эту версию не включено. Номера FR, NFR, US сохраняются до конца семестра и не переиспользуются. Для этой работы используется система FR/NFR/US из задания ЛР2; отдельный ряд UR не вводится.

| Номер | Формулировка | Приоритет | Состояние | Признак выполнения |
| --- | --- | --- | --- | --- |
| FR-1 | Пользователь (заявитель или специалист) может войти в систему с учётными данными и получить доступ согласно своей роли. | Обязательно | Нужно сделать | Верные данные дают доступ; неверные — отказ без создания сессии. |
| FR-2 | Пользователь (заявитель) может создать заявку с заголовком, описанием и категорией. | Обязательно | Нужно доработать | Создана одна заявка с уникальным ID, автором и статусом open; пустые поля и неизвестная категория отклоняются без записи. |
| FR-3 | Пользователь (заявитель или специалист) может просматривать свои заявки или общую очередь соответственно роли. | Обязательно | Нужно доработать | Заявитель получает только свои заявки, специалист — все; пустой результат представлен пустым списком. |
| FR-4 | Пользователь (заявитель или специалист) может открыть доступную ему заявку и увидеть её данные и обсуждение. | Обязательно | Нужно сделать | Карточка содержит ID, заголовок, описание, автора, категорию, статус, исполнителя и комментарии; чужой заявитель и неизвестный ID получают отказ. |
| FR-5 | Пользователь (специалист) может назначить себя исполнителем открытой заявки. | Обязательно | Нужно сделать | Для open без исполнителя сохраняется текущий специалист; повтор того же назначения не меняет результат, замена другого исполнителя отклоняется. |
| FR-6 | Пользователь (назначенный специалист) может перевести свою заявку из open в in_progress и из in_progress в closed. | Обязательно | Нужно сделать | Разрешённые переходы сохраняются; пропуск этапа, обратный переход и действия другого специалиста отклоняются без изменения. |
| FR-7 | Пользователь (заявитель-автор или специалист) может добавлять и читать комментарии доступной заявки. | Обязательно | Нужно сделать | Непустое сообщение сохраняется с автором и временем; чужой заявитель и запись в closed получают отказ. |
| FR-8 | Пользователь (заявитель) может получить список категорий и выбрать существующую категорию при создании заявки. | Обязательно | Нужно сделать | Возвращаются категории с ID и названием; создание принимает только ID из справочника. Изменение категории после создания вне объёма. |

### 2.2. Нефункциональные ограничения

Все ограничения обязательны; сейчас требуют реализации или полной проверки.

| Номер | Ограничение | Состояние | Проверка |
| --- | --- | --- | --- |
| NFR-1 | Приложение собирается Go 1.24.5 и запускается в Linux-контейнере на amd64 и arm64 не более чем пятью командами из README. | Нужно доработать | Чистая сборка и smoke по инструкции на обеих архитектурах; пока проверена arm64. |
| NFR-2 | При 10 одновременных клиентах и базе 1000 заявок 95-й процентиль времени GET списка и карточки не превышает 500 мс, доля серверных ошибок — 0% за 60 секунд на машине с 2 CPU и 2 ГБ RAM. | Нужно проверить | Нагрузочный отчёт с указанной средой, раздельными измерениями двух операций. |
| NFR-3 | Все операции с заявками требуют действующей сессии, пароли хранятся только в виде стойких хешей, заявитель не получает данные чужих заявок. | Нужно сделать | Без сессии — 401; чужая карточка — 404, чужие ID отсутствуют в списке; проверка БД не обнаруживает открытых паролей. Для развёртывания вне localhost требуется HTTPS. |
| NFR-4 | После успешного ответа о создании или изменении заявки данные, комментарии и связи сохраняются после перезапуска приложения с тем же файлом SQLite. | Нужно сделать | Создать, назначить, изменить статус, добавить комментарий, перезапустить и сравнить поля. |
| NFR-5 | Неверный JSON, неизвестные поля и незаполненные обязательные поля отклоняются с 400 без изменения данных; тело запроса свыше 4096 байт отклоняется с 413. | Нужно доработать | Сравнить данные до и после запросов; проверить каждый случай, включая лишний JSON после первого объекта. |

Планируемые ошибки API: JSON вида `{"error":"код"}`. Коды: invalid_request (400), invalid_credentials / unauthorized (401), forbidden (403), not_found (404), invalid_transition / already_assigned / ticket_closed (409), payload_too_large (413). Это целевой контракт, текущие текстовые ошибки прототипа будут заменены. Для заявителя чужая и несуществующая заявка одинаково дают 404. Внешнее сообщение клиенту — значение error, локализация вне объёма.

## 3. Пользовательские сценарии

### US-1. Вход

Требование: **FR-1**. Состояние: **Нужно сделать**.

Я как **заявитель или специалист** имею существующую учётную запись, логин и пароль, делаю: Передаю логин и пароль. При успехе сохраняю полученный токен сессии. Получаю токен сессии и роль; могу выполнять разрешённые операции.

- **Вход:** существующую учётную запись, логин и пароль.
- **Выход:** токен сессии и роль; могу выполнять разрешённые операции.

### US-2. Создание заявки

Требование: **FR-2**. Состояние: **Нужно доработать: есть создание только по title**.

Я как **заявитель** имею действующую сессию, title, description и category_id из справочника, делаю: Выбираю категорию. Ввожу заголовок и описание. Отправляю заявку. Получаю 201 и созданную заявку с новым ID, своим авторством, статусом open и пустым исполнителем.

- **Вход:** действующую сессию, title, description и category_id из справочника.
- **Выход:** 201 и созданную заявку с новым ID, своим авторством, статусом open и пустым исполнителем.

### US-3. Просмотр списка

Требование: **FR-3**. Состояние: **Нужно доработать: есть общий список без ролей**.

Я как **заявитель или специалист** имею действующую сессию, делаю: Запрашиваю список заявок. Просматриваю полученные элементы. Получаю заявитель — только собственные заявки; специалист — общую очередь; данные не меняются.

- **Вход:** действующую сессию.
- **Выход:** заявитель — только собственные заявки; специалист — общую очередь; данные не меняются.

### US-4. Просмотр карточки

Требование: **FR-4**. Состояние: **Нужно сделать**.

Я как **заявитель-автор или специалист** имею действующую сессию и ID доступной заявки, делаю: Выбираю заявку из списка. Открываю карточку. Получаю поля заявки и комментарии по времени добавления, при равном времени — по ID; данные не меняются.

- **Вход:** действующую сессию и ID доступной заявки.
- **Выход:** поля заявки и комментарии по времени добавления, при равном времени — по ID; данные не меняются.

### US-5. Принятие заявки

Требование: **FR-5**. Состояние: **Нужно сделать**.

Я как **специалист** имею сессию и ID заявки open без исполнителя, делаю: Открываю заявку. Выполняю действие «Взять в работу» (назначить себя). Получаю я указан исполнителем; статус остаётся open до отдельного начала обработки.

- **Вход:** сессию и ID заявки open без исполнителя.
- **Выход:** я указан исполнителем; статус остаётся open до отдельного начала обработки.

### US-6. Обработка заявки

Требование: **FR-6**. Состояние: **Нужно сделать**.

Я как **назначенный специалист** имею сессию, ID назначенной мне заявки и целевой статус, делаю: Перевожу open в in_progress. После решения проблемы перевожу in_progress в closed. Получаю сохранённый новый статус; завершённая заявка остаётся доступной для чтения.

- **Вход:** сессию, ID назначенной мне заявки и целевой статус.
- **Выход:** сохранённый новый статус; завершённая заявка остаётся доступной для чтения.

### US-7. Обсуждение

Требование: **FR-7**. Состояние: **Нужно сделать**.

Я как **заявитель-автор или специалист** имею сессию, ID доступной незакрытой заявки и непустой текст, делаю: Открываю обсуждение. Ввожу текст. Отправляю и читаю комментарии. Получаю 201, ID комментария, текст, автора и время; сообщение присутствует в обсуждении.

- **Вход:** сессию, ID доступной незакрытой заявки и непустой текст.
- **Выход:** 201, ID комментария, текст, автора и время; сообщение присутствует в обсуждении.

Требование: **FR-8**. Состояние: **Нужно сделать**.

Я как **заявитель** имею действующую сессию, делаю: Получаю справочник категорий. Выбираю category_id. Передаю его при создании заявки по US-2. Получаю список ID и названий; выбранная категория связана с созданной заявкой.

- **Вход:** действующую сессию.
- **Выход:** список ID и названий; выбранная категория связана с созданной заявкой.

### 3.1. Конкретные примеры трёх ключевых сценариев

Примеры целевые, пока не реализованы полностью. Данные каждого примера независимы; это заранее подготовленные фикстуры, а не предположение о текущем счётчике ID. Пользователь 1 — заявитель Анна, 2 — специалист Илья, 3 — другой заявитель; категория 1 — «Доступ к сервисам». Время фиксируется тестовыми часами. Строки обрезаются по краям до проверки непустоты.

**US-2 / FR-2 — создание.** В базе нет заявок, следующая ID — 1. Вход: сессия пользователя 1 и `{"title":"Не работает VPN","description":"Ошибка подключения 691","category_id":1}`. Ожидается 201 и `{"id":1,"title":"Не работает VPN","description":"Ошибка подключения 691","category_id":1,"author_id":1,"assignee_id":null,"status":"open"}`. В хранилище ровно одна новая заявка.

Неверный вход: тот же запрос с `"title":"   "` → 400 `{"error":"invalid_request"}`. Неполный вход без description или category_id → тот же ответ; неизвестный category_id=999 → тот же ответ. Ни один случай не создаёт заявку; список и счётчик записей не меняются.

**US-6 / FR-6 — изменение статуса.** Дана заявка 7 в open с assignee_id=2. Вход: сессия пользователя 2 и `{"status":"in_progress"}` для заявки 7. Ожидается 200 `{"id":7,"status":"in_progress"}`; остальные поля сохраняются. Следующий запрос `{"status":"closed"}` → 200 `{"id":7,"status":"closed"}`.

Неверный переход: из open сразу в closed → 409 `{"error":"invalid_transition"}`. Неполный запрос `{}` или неизвестный статус → 400 `{"error":"invalid_request"}`. Заявитель либо другой специалист → 403 `{"error":"forbidden"}`. Во всех ошибочных случаях исходное состояние сохраняется. Из closed переходов нет; повтор статуса отклоняется как invalid_transition.

**US-7 / FR-7 — комментарий.** Дана заявка 7 в in_progress с author_id=1, assignee_id=2, комментариев нет. Следующий ID комментария — 1, тестовое время — `2026-11-13T12:00:00Z`. Вход: сессия пользователя 1 и `{"text":"После смены пароля VPN заработал"}`. Ожидается 201 `{"id":1,"ticket_id":7,"author_id":1,"text":"После смены пароля VPN заработал","created_at":"2026-11-13T12:00:00Z"}`. В обсуждении ровно одно новое сообщение, статус заявки не меняется.

Неверный/неполный вход: `{"text":"   "}` или `{}` → 400 `{"error":"invalid_request"}`. Заявка closed → 409 `{"error":"ticket_closed"}`. Сессия пользователя 3 → 404 `{"error":"not_found"}`. Новых сообщений и изменений заявки нет.

### Вопросы для ревью

Выбранные в версии 1.0 правила требуют подтверждения: отсутствие переназначения и повторного открытия, запрет комментариев в closed, предварительное наполнение пользователей и категорий. Они описаны как единый целевой контракт, но одобрение преподавателем не заявляется. Связанные открытые вопросы: #2 (хранение), #3 (доступ), #4 (статусы). Их закрытие требует фактического согласования и последующей реализации.

Ревью проводится через PR lab-2 → main другим студентом, назначенным преподавателем. Требуется содержательный комментарий к конкретному месту, ответ автора, исправление отдельным коммитом или обоснование, затем resolve и approve. Подготовленный текст PR и порядок завершения: [lab-2-review.md](lab-2-review.md).
