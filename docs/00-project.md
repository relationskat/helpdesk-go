# Паспорт проекта: HelpDesk Go

## Исходное описание

**Происхождение:** новый проект с нуля. Начальный коммит `dba8e5e` содержит README и MIT LICENSE. Это не форк: upstream и журнал запуска стороннего проекта не применяются.

**Назначение:** учёт обращений пользователей небольшой организации в техническую поддержку. Решаемая проблема — потеря обращений и истории обработки в переписке.

**Целевые пользователи и роли:** заявитель создаёт и отслеживает свои обращения; специалист поддержки видит очередь, назначает исполнителя, отвечает и завершает обработку. Контроль доступа в скелете ЛР1 ещё не реализован.

**Три основные функции:** создание заявки; обработка со сменой статуса; обсуждение результата и отслеживание обращения.

**Четыре сущности:** пользователь (учётная запись и роль), заявка (автор, описание, статус, исполнитель, категория), комментарий (заявка, автор, текст, время), категория (название, описание направления поддержки). Роль и статус — атрибуты.

**Стек:** Go 1.24.5, стандартные net/http и encoding/json, HTTP/JSON, Docker, GitHub Actions. Сейчас память процесса; SQLite и конкретный драйвер планируется выбрать на этапе архитектуры. Клиент скелета — curl.

**Лицензия:** MIT, сохранена из исходного состояния.

**Команда:** индивидуально, владелец GitHub `relationskat` — аналитик, разработчик, тестировщик, ответственный за выпуск. По git author: Нурлыгаянова Екатерина; группа не предоставлена, её нужно дополнить перед сдачей.

**Репозиторий:** https://github.com/relationskat/helpdesk-go. Согласование преподавателем не подтверждено. Product: [#1](https://github.com/relationskat/helpdesk-go/issues/1), открыт; [локальный текст](issues/product.md).

| Каталог / файл | Назначение |
| --- | --- |

| docs/00-project.md | Паспорт, карта и план |
| docs/01-requirements.md — 05-deployment.md | Заготовки последующих работ |
| docs/adr/, docs/diagrams/ | Решения и исходники диаграмм; пока .gitkeep |
| docs/issues/ | Подготовленные тексты issues |
| evidence/ | Фактические результаты запуска |

Скелет организован по образцу собственного проекта `mtusi2026lab7`: config → сборка зависимостей в main; api/http → service → store, отдельные domain и DTO. Использована структура слоёв, реализация HelpDesk самостоятельная на стандартной библиотеке Go.

Внешние БД, очереди и API приложению сейчас не нужны. Docker Hub используется для образа сборки, GitHub — для репозитория и CI. Заявки хранятся в памяти, доступ защищён mutex; после остановки исчезают. Конфигурация — переменная ADDR, файла настроек нет; публикация порта задаётся Docker -p, адрес smoke-проверки — BASE_URL.

## Карта функций

Всего восемь пользовательских функций. Существующие слои расширяются в следующих работах; файлы auth, comments и categories пока планируются.

| Функция | Состояние и модуль | Ручная проверка |
| --- | --- | --- |
| Вход с ролью | План: src/internal/service/auth.go и src/internal/api/http/auth.go | Войти заявителем и специалистом; неверный пароль отклоняется |
| Создание заявки | Прототип: src/internal/api/http/tickets.go → service/tickets.go → store/memory.go, POST /tickets | JSON с title даёт 201 и ID; пустой title — 400 |
| Список своих заявок / очередь | Прототип: src/internal/api/http/tickets.go → service/tickets.go → store/memory.go, GET /tickets; фильтрация планируется | Создать и найти заявку; после реализации ролей проверить изоляцию |
| Карточка заявки | План: src/internal/service/tickets.go и src/internal/api/http/tickets.go | Получить по ID, неизвестный ID отклоняется |
| Назначение исполнителя | План: src/internal/service/tickets.go и src/internal/api/http/tickets.go | Специалист берёт заявку; заявителю отказ |
| Изменение статуса | План: src/internal/service/tickets.go и src/internal/api/http/tickets.go | open → in_progress → closed, запрет неверного перехода |
| Комментарии | План: src/internal/service/comments.go и src/internal/api/http/comments.go | Оставить и прочитать сообщение; запрет чужой заявки |
| Выбор категории | План: src/internal/service/categories.go и src/internal/api/http/categories.go | Выбрать существующую; неизвестная отклоняется |

GET /healthz — техническая проверка, не пользовательская функция. Реализованный сценарий автоматизирован в tests/smoke.sh; планируемые сценарии пока недоступны.

## Выполнимость и план

| Риск | Вероятность | Последствия | Снижение |
| --- | --- | --- | --- |
| Технический: незнакомые SQLite и миграции | Средняя | Задержка, потеря данных при изменении схемы | Прототип, один драйвер, тест миграции и перезапуска |
| Технический: ошибки прав доступа | Средняя | Доступ к чужим заявкам | Матрица прав, отрицательные API-тесты |
| Технический: гонки и статусы | Средняя | Несогласованные данные | Транзакции, таблица переходов, go test -race |
| Организационный: один участник и ограниченное время | Высокая | Срыв сроков | 8 функций без UI, резерв 10 часов, небольшие PR |
| Внешний: недоступность Docker Hub / GitHub | Средняя | Нет образов или CI | Локальная сборка Go, кеш образов, заранее проверить доступ |
| Внешний: лицензия будущего драйвера | Низкая | Ограничение распространения | Проверить до добавления зависимости |
| Внешний: изменение объёма преподавателем | Средняя | Переработка плана | Согласовать product до ЛР2 |

Платные API, ключи и облачная БД не требуются. HTTP-скелет демонстрирует техническую выполнимость основной функции. Оставшийся объём — 64 часа плюс 10 часов резерва; предварительно выполним за семестр.

Ответственный за все работы — relationskat.

| Работа | План | Часы |
| --- | --- | --- |
| ЛР2 | Согласовать роли, восемь функций, статусы, критерии приёмки, NFR; ввести UR/FR/NFR и трассировку. | 10 |
| ЛР3 | Валидировать сценарии с преподавателем, устранить противоречия прав и статусов, оформить CR. | 8 |
| ЛР4 | Развить слои HTTP, доменной логики и хранилища; оформить диаграммы и ADR, реализовать SQLite, роли и согласованные функции. | 26 |
| ЛР5 | Модульные и API-тесты с T, отрицательные проверки доступа, статусов и сохранности; отчёт о тестировании. | 12 |
| ЛР6 | Версионная сборка, миграции, развёртывание и восстановление, CHANGELOG и выпуск. | 8 |

В объём входят восемь функций карты, локальное развёртывание и SQLite. За пределами: вложения, email/мессенджеры, SSO, SLA, отчётность, мобильное приложение, полноценный UI, многосерверная установка. Окончательные границы — в ЛР2.

### Условия завершения

Product и три вопроса опубликованы. Необходимо назначить вопросам метку question, создать остальные метки и настроить защиту main. Публичный репозиторий доступен преподавателю для чтения кода, issues и PR; преподавателю нужно передать ссылку. Получить одобрение выбора и плана в product; только затем закрыть product, слить PR lab-1 → main и поставить тег lab-1 на итоговый коммит. Согласование не заменяется подготовкой файлов.
